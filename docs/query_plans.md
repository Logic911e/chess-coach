# Query plans and index choices

All numbers are from a **synthetic** benchmark database (`chess_coach_bench`): 2,000 games,
138,980 moves, 138,980 evaluations and 15,470 facts, generated by `scripts/seed_synthetic.sql`
with a fixed random seed. Reproduce with:

```bash
docker-compose up -d
PYTHONPATH=src python scripts/seed_synthetic.py        # builds the bench DB
PYTHONPATH=src python scripts/explain.py after         # median of 7 EXPLAIN (ANALYZE, BUFFERS) runs
PYTHONPATH=src:scripts python scripts/index_experiments.py   # candidate indexes, one at a time
```

Raw plans are in `docs/plans/baseline/` (no migration 003) and `docs/plans/after/`.

## What was measured, and what was kept

Median of 7 runs on a laptop that was not idle, so run-to-run noise was roughly ±10-30%.
Treat the ratios as meaningful and the absolute milliseconds as approximate.

| Query | Before | After | Change |
|---|---|---|---|
| `worst_moment_per_game_of_player` (RANK window) | 26.1 ms | 5.9 ms | ~4.4x faster |
| `blunders_of_player` | 21.9 ms | 4.8 ms | ~4.6x faster |
| `facts_rare_pattern` (JSONB, 3.3% of rows) | 3.1 ms | 1.0 ms | ~3x faster |
| `facts_ignored_knight_threat` (JSONB, 26% of rows) | 3.4 ms | 2.7 ms | small |
| `rolling_error_one_game` (window) | 0.24 ms | 0.23 ms | already indexed |
| `phase_error_rate`, `opening_error_rate` | 60 / 285 ms | 72 / 232 ms | no real change (noise) |

**Kept (migration 003):**

1. `moves (game_id, color, ply)`. Before, the planner hash-joined and seq-scanned all 138,980
   `moves` rows to find one player's ~2,700 moves. After, it runs 80 index scans, one per game
   of that player, each returning about 34 rows. The existing `UNIQUE (game_id, ply)` index could
   not be used for the `color` filter.
2. GIN `facts jsonb_path_ops`. The plan changes from `Seq Scan on facts` to
   `Bitmap Index Scan on facts_gin_idx` for the selective containment query.

**Measured and rejected** (`docs/index_experiments.txt`): `games(white)` / `games(black)`
(the `games` table is only 41 pages, so a seq scan costs 0.2 ms), a partial index on blunders, and
a covering index on `evaluations`. None made any query meaningfully faster, so they would only
slow writes and take disk.

**Not helped by any index:** `phase_error_rate` and `opening_error_rate` read every row on purpose
(they aggregate the whole table). The honest fix for those is pre-aggregation, such as a
materialised view refreshed after each import, which I have not built.

## Limits of this evidence

- The data is synthetic. Row counts and the share of errors (about 9%) are realistic; the
  distribution is not. Blunders outnumber mistakes because the generated loss is capped at 1.
- Everything ran from cache (`Buffers: shared hit` only, no disk reads), so cold-cache behaviour is
  not measured.
- One machine, one Postgres 17 container, default settings.
- The real database (`chess_coach`) holds no analysed games yet.
